# Проверка бэкенда и интеграции с ML

Дата: 26 октября 2026 года. База проверки - `86a1f72`, ветка `dev`.
Код менялся только в `backend/`; общие compose/Makefile/CI обслуживают проверки и настройки бэкенда.
Код `ml/` и `frontend/` в этой работе не редактировался. При синхронизации `dev` сохранены уже опубликованные
изменения ML-команды (`b3e11ef`, merge `7b340b4`) без правок. Документация описывает все части проекта.

## Что исправлено

1. Новая ручная генерация получает новый ML `request_id`, а HTTP-повторы сохраняют его.
2. Повреждённый ответ генератора и SSE обрабатываются как записанные ошибки. Таймауты и run-токены
   согласованы с длительностью вопросов и HTTP-повторов.
3. Gateway проверяет JSON, сообщения, usage и баланс провайдера до передачи агенту; повреждённый
   HTTP 200 становится `502 llm-invalid-response` с освобождением резерва бюджета.
4. `SCORER_PROVIDER=remote` подключён ко всем путям матчинга: проверяемые батчи до 500, разделение по
   ролям, fallback на baseline, снятие старых карточек при утрате релевантности.
5. Настоящий ML возвращает имя скорера длиной 33 символа. Миграция **0011** расширяет поле с 32 до 255,
   устраняя найденный сквозным тестом сбой seed. ORM и миграции проверены на отсутствие дрейфа.
6. Двенадцать настроек таймаутов, CORS, SSE, дайджестов, rate limit и LLM передаются из окружения Compose
   во все процессы бэкенда. Seed подключён к общей сети для доступа к отдельно развёрнутому ML.
7. Добавлен отдельный `make e2e-ml` с исходным сервисом ML. Старый тест исчерпания бюджета использует
   фиксированный тестовый тариф, чтобы не зависеть от изменения реальных цен.

## Границы результата

- Платные вызовы живого LLM-провайдера и деплой на удалённый стенд не выполнялись. Наличие тестов CI
  в YAML не означает завершённый прогон GitHub Actions или успешный деплой.
- `e2e-ml` проверяет настоящий HTTP-протокол и агент по правилам. LLM и семантические модели отключены;
  этот результат не является оценкой качества генерации на живой модели.
- Remote-скоринг действует на baseline-shortlist. Семантический ранкер внутри агента - отдельный этап.
- Перед включением remote на существующей базе нужно выполнить `alembic upgrade head` (до 0011).
- Кэш/идемпотентность ML остаются локальными для процесса. Их ограничения и отмена concurrent-запросов
  требуют отдельной работы команды ML; код ML в этой задаче не менялся.

## Дополнение: комплект сдачи и доступность стенда

После сверки со страницей 8 задания добавлена [памятка сдачи](SUBMISSION.md), исправлены пути
в SPEC и устаревшие сведения о проверках, дополнены THIRD_PARTY_NOTICES.
В notices фронтенда перечислены все 346 уникальных production-пар «пакет + версия» из lock-файла;
условия, отсутствующие в метаданных, явно помечены. `make notices`, ruff и формат генератора прошли.

GitHub API подтвердил публичный доступ к репозиторию. Удалённый dev-стенд ответил HTTP 200:
страница, OpenAPI и вход демо-учётки. По API проверены 3 доступные компании, разные ленты
`U_700001`/`U_700002` (20/12 карточек), источники и персонализация двух инсайтов.
Вызовы LLM и CRM-заявки при этой проверке не выполнялись. Проверка опубликованного стенда
не означает, что локальные исправления уже доставлены: финальную публикацию и SHA нужно зафиксировать отдельно.

## Проверка после синхронизации с ML-командой

Коммиты команды интегрированы без изменения её ML-кода. Полный `make check` после merge успешен:
478 unit и 84 integration, один локальный skip Tesseract; ML - 57 тестов, `e2e-ml` - 3 теста.
Затем Gateway бэкенда получил отдельную совместимость: повтор без optional-поля, которое провайдер
явно отверг как неподдерживаемое. После этого ruff/mypy и все **484 unit** прошли; отдельно прошли
**12 интеграционных тестов Gateway**. Ограничение: платный LLM при этих прогонах не вызывался.
