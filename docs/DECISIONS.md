# Архитектурные решения (ADR)

Формат: контекст → решение → альтернативы → последствия. Новые ADR добавляются в конец.

## ADR-001: Базовый стек бэкенда
- Дата: 2026-10-22 · Статус: принято
- Контекст: хакатон, команда Python-ориентирована, ML-часть на Python, нужен OpenAPI «из коробки».
- Решение: Python 3.12, uv (`uv.lock`), FastAPI, Pydantic v2, SQLAlchemy 2 async + asyncpg, Alembic, structlog, prometheus-client.
- Альтернативы: Go/Java — быстрее в рантайме, но дольше разработка и хуже стык с ML.
- Последствия: единый язык с ML-командой; OpenAPI генерируется из кода и коммитится в `docs/openapi.json`.

## ADR-002: Одна PostgreSQL 16 + pgvector; граф связей в таблицах
- Дата: 2026-10-22 · Статус: принято
- Контекст: нужны реляционные данные (~85 тыс. компаний, ~1,4 млн платежей), векторный поиск (сотни/тысячи чанков и новостей), граф связей.
- Решение: векторы в той же БД (`vector(N)`, HNSW, cosine), полнотекст — `tsvector('russian')`; граф — таблица `company_edges` + recursive CTE.
- Альтернативы: Qdrant/Weaviate (лишний сервис, нет джойнов с метаданными), Neo4j (лишний сервис; глубина обхода у нас ≤ 2).
- Последствия: гибридный поиск одним SQL-запросом; при росте объёма векторов — партиционирование или вынос в отдельное хранилище за `VectorStore`-интерфейсом.

## ADR-003: Очереди — Taskiq + Redis
- Дата: 2026-10-22 · Статус: принято
- Контекст: фоновые задачи (ingest, OCR, эмбеддинги, генерация инсайтов, дайджесты) и периодический сбор новостей.
- Решение: Taskiq (`taskiq-redis` broker + result backend) и `taskiq scheduler` отдельным процессом (`scheduler` в compose).
- Альтернативы: arq — проще, но в режиме поддержки и планировщик живёт внутри воркера; Celery — тяжёлый, слабая поддержка asyncio.
- Последствия: воркеры масштабируются горизонтально (`docker compose up --scale worker=N`); задачи идемпотентны по ключу.

## ADR-004: S3-хранилище — MinIO
- Дата: 2026-10-22 · Статус: принято
- Решение: MinIO (S3 API), бакеты `analytics` (PDF + OCR-кэш), `news-raw` (сырые ответы источников), `snapshots` (выгрузки/датасеты). Создаются `minio-init` и при старте API (idempotent). Клиент — boto3 (в потоке) за интерфейсом `ObjectStore`.
- Последствия: presigned URL для скачивания PDF; в проде заменяется на любой S3 без изменения кода.
- Дополнение (2026-10-22): официальные образы `minio/minio` и `minio/mc` больше не публикуются (Docker Hub и quay.io отвечают
  `pull access denied`). Используем `pgsty/minio:RELEASE.2026-08-04T00-00-00Z` — сборку MinIO из исходников (AGPL-3.0), в образе есть `mc`.
  Код работает только через S3 API, поэтому запасные варианты без изменения кода — SeaweedFS или RustFS.

## ADR-005: Аналитика банка — OCR обязателен
- Дата: 2026-10-22 · Статус: принято
- Контекст: профилирование показало, что все 9 PDF — сканы без текстового слоя (0 символов).
- Решение: пайплайн «текстовый слой (pypdfium2, ADR-023) → если < 200 символов на странице, OCR». `OcrProvider`:
  `tesseract` (по умолчанию, `tesseract-ocr` + `rus` в образе воркера, 300 dpi рендер), `vlm` (Qwen3-VL-30B-A3B-Instruct
  из белого списка, **только через LLM Gateway**, под флагом — для таблиц/графиков), `fake` (тесты). Результат OCR кэшируется в S3 по sha256 файла.
- Альтернативы: только VLM — тратит дневной бюджет; PaddleOCR/EasyOCR — тяжёлые зависимости (torch).
- Последствия: в образе воркера +~60 МБ; качество OCR фиксируется в `analytics_documents.extraction` (метод, средняя уверенность).

## ADR-006: Эмбеддинги — fastembed (ONNX) за интерфейсом
- Дата: 2026-10-22 · Статус: принято; модель выбирает ML-команда
- Контекст: в задании по умолчанию sentence-transformers; ограничений на эмбеддинги нет (FAQ п.6).
- Решение: `EmbeddingProvider` с реализациями `fake` (детерминированный хэш-вектор, тесты), `local` (fastembed — те же
  open-source модели в ONNX, без torch; образ меньше в ~5 раз), `remote` (OpenAI-совместимый `/embeddings`, например TEI).
  `EMBEDDING_MODEL` и `EMBEDDING_DIM` в env. Бэкенд поставляет только провайдеры; модель задаёт ML-команда,
  без неё `local`/`remote` не стартуют с понятной ошибкой.
- Альтернативы: sentence-transformers + torch CPU (+~1,5 ГБ к образу).
- Последствия: смена модели = миграция размерности колонки + переиндексация
  (`uv run python scripts/ingest.py analytics --reembed`); поиск сравнивает векторы только своей модели
  (`analytics_documents.embedding_model`), до переиндексации работает полнотекстовая часть.
- Уточнение (фаза 5): выбор модели — зона ML, поэтому в compose по умолчанию `EMBEDDING_PROVIDER=fake` и
  пустой `EMBEDDING_MODEL`; после выбора модели ML-командой — `local` (кэш в томе `models`) или `remote` и
  переиндексация `scripts/ingest.py analytics --reembed`.
  При недоступности модели поиск использует полнотекстовую часть без подстановки тестовых векторов (ADR-026).
  В тестах и e2e — явно выбранный `fake`.

## ADR-007: Baseline на правилах за интерфейсами; ML заменяет
- Дата: 2026-10-22 · Статус: принято
- Контекст: граница с ML (классификация новостей, NER, скоринг, генерация).
- Решение: бэкенд поставляет детерминированные baseline-реализации: тегирование новостей по словарям (ОКВЭД-секции, страны, регионы, тип события),
  `RelevanceScorer` (взвешенная сумма признаков с breakdown), `InsightGenerator` = `ml_stub` (шаблоны). Каждая — за Protocol в `app/domain/ports.py`, выбор через env.
- Последствия: сквозной сценарий и e2e не зависят от ML; ML подключается реализацией `remote` по контрактам из `contracts/`.

## ADR-008: Контракт инсайта v1.0.0
- Дата: 2026-10-22 · Статус: принято (до согласования с ML/фронтом — draft)
- Решение: JSON Schema `contracts/insight.schema.json` (draft 2020-12) + зеркальные Pydantic-модели `app/domain/contracts/insight.py`.
  Ключевые поля в колонках `insights`, полный payload — `jsonb`. Утверждения (`statements[]`) с `kind` ∈ {fact, bank_analytics, model_inference, hypothesis}.
  Шкала влияния: low/medium/high/critical + score 0–100 (`docs/IMPACT_SCALE.md`, `scale_version`).
- Последствия: валидатор = JSON Schema + бизнес-правила; невалидные — в `insights_rejected` с причинами.

## ADR-009: Идентификаторы компаний и коллизия `U_428697`
- Дата: 2026-10-22 · Статус: принято
- Контекст: `U_428697` встречается 12 раз (артефакт обезличивания, FAQ п.17); строки разные.
- Решение: `core.companies.id = SYNTHETIC_U` (text PK). Для коллизии создаётся **одна** запись-маркер с `is_valid=false`,
  `invalid_reason='pseudo_id_collision'`, без бизнес-полей (не схлопываем данные 12 строк в одну компанию); все исходные строки
  сохраняются в `staging.companies_raw` с номером строки. Платежи с этой стороной помечаются `party_invalid=true` и не участвуют в графе.
- Последствия: FK на `companies.id` работают; такие компании не попадают в ленту/контекст.

## ADR-010: Аутентификация и роли
- Дата: 2026-10-22 · Статус: принято
- Решение: JWT HS256 (access 30 мин + refresh 7 дней), демо-учётки из seed (пароли — bcrypt-хэши). Роли платформы: `user`, `admin`, `service`.
  Роль пользователя в компании (`owner/ceo/cfo/chief_accountant/treasurer/other`) — в `user_company_access`, переключается вручную (FAQ п.31).
  Проверка полномочий в компании считается выполненной интернет-банком (FAQ п.32) — эмулируется таблицей доступа.
- Последствия: каждый запрос к данным компании проходит `require_company_access`; Tools API — сервисный токен + scope `run_id`.

## ADR-011: Доставка в реальном времени — SSE + Redis pub/sub
- Дата: 2026-10-22 · Статус: принято
- Решение: `GET /api/v1/notifications/stream` (SSE), события публикуются воркером в Redis-канал `notify:user:{id}`; стриминг ответов на вопросы — SSE.
- Альтернативы: WebSocket — двунаправленность не нужна; polling — хуже UX для срочных событий.

## ADR-013: ml_stub
- Дата: 2026-10-22 · Статус: принято
- Решение: отдельный сервис `ml-stub` реализует `contracts/ml-service.openapi.yaml` детерминированно: ходит в Tools API бэкенда (как настоящий агент),
  пишет шаги через `log_step`, собирает инсайт по шаблонам из признаков компании, события и найденных чанков аналитики.
  LLM не вызывает: промпты и генерация текста — зона ML-команды; ml-stub только детерминированная замена агента.
- Последствия: трассировка и валидатор проверяются на «настоящем» потоке вызовов.

## ADR-015: Граф связей — рёбра только между валидными компаниями, группа не материализуется
- Дата: 2026-10-22 · Статус: принято
- Контекст: 1,38 млн пар платежей, 30–42% строк — с неизвестными контрагентами; крупнейшая группа — 624 юрлица.
- Решение: `core.company_edges` хранит `payment` (доли от полного оборота направления, включая неизвестных контрагентов,
  без самопереводов), `shared_person` и `hypothesis` (`key_supplier`, `key_customer`, `affiliated_outside_group`) с
  `confidence` и `evidence`. Платежи с неизвестными сторонами остаются в `payments_agg` и учитываются в долях
  (`counterparties.unknown_share_*`), но рёбер не дают. Принадлежность к группе — `companies.group_id`, попарно не хранится.
- Альтернативы: клика по группе (~195 тыс. рёбер для одной группы); узлы-заглушки для неизвестных компаний (выдумывание профиля — запрещено FAQ п.22).
- Последствия: на реальных данных 439 тыс. рёбер; гипотезы явно помечены и не выдаются как факты.

## ADR-016: Сегмент масштаба и порог среднего бизнеса
- Дата: 2026-10-22 · Статус: принято
- Контекст: кейс определяет крупный бизнес как выручку > 15 млрд ₽ по группе (FAQ п.16); нижняя граница среднего не задана.
- Решение: `segment` = `large` (> 15 млрд), `mid` (≥ 0,8 млрд — верхняя граница малого бизнеса по 209-ФЗ / ПП РФ № 265),
  `small`, `unknown`; база — выручка группы, если известна, иначе своя. Признак производный (`source=derived`) и используется
  как характеристика масштаба, а не как фильтр доступа.

## ADR-017: Загрузка компаний — COPY в staging, set-based SQL, пересчёт контекста батчами
- Дата: 2026-10-22 · Статус: принято
- Решение: три CSV грузятся `COPY` (asyncpg `copy_to_table`) в `staging.*` как текст; очистка уровня строки — чистые функции
  `app/domain/cleaning.py`; платежи, физлица, граф — set-based SQL; контекст — агрегаты по контрагентам во временных таблицах
  + сборка признаков в Python батчами по 5 000 компаний. Повторный прогон идемпотентен: upsert компаний, сохранение
  `user_provided`, `context_version + 1`, компании, исчезнувшие из выгрузки, помечаются `absent_in_latest_load`.
- Последствия: полная загрузка реальных данных (85,5 тыс. компаний, 1,38 млн платежей) — ~2,5 мин на ноутбуке
  (NFR-2 < 10 мин); синтетика — ~9 с. Пересчёт контекста одной компании после правки профиля — доли секунды.

## ADR-018: Монорепозиторий с разделением на backend/, ml/, frontend/
- Дата: 2026-10-22 · Статус: принято (запрос владельца репозитория)
- Решение: код бэкенда — в `backend/` (свой `pyproject.toml`/`uv.lock`, Dockerfile, тесты); `ml/` и `frontend/` — зоны
  других команд; общие артефакты в корне: `contracts/` (контракты между командами), `docs/`, `docker-compose*.yml`
  (единый запуск всей системы), `Makefile`, CI, `data/raw/` (данные организаторов, не коммитятся).
  Docker-образ бэкенда собирается из корня (`-f backend/Dockerfile .`), чтобы включить `contracts/`; каталог контрактов
  код находит поиском вверх по дереву или через `CONTRACTS_DIR`.
- Последствия: команды Python запускаются из `backend/` (`make` делает это сам); история файлов сохранена (`git mv`).

## ADR-019: Поток генерации инсайта и очередь
- Дата: 2026-10-22 · Статус: принято
- Решение: кандидат `pending` → `agent_runs` + run-токен (JWT, `typ=run`, компания и `run_id`, TTL = таймаут + 60 с) →
  `POST /v1/insights/generate` у ML-сервиса (`ml-stub` по умолчанию) → агент ходит в `/internal/tools/*` →
  валидатор (JSON Schema + бизнес-правила) → `insights` (upsert по компании × событию × роли) или `insights_rejected`.
  Бэкенд пишет в трейс свои шаги (`backend.request`, `backend.validate`, `backend.persist`), агент — свои через `log_step`,
  вызовы инструментов — в `tool_audit_log`. Очередь Taskiq переведена на `ListQueueBroker` (Redis list): сообщения, поставленные
  сидом до старта воркера, не теряются (у Redis Streams группа создаётся с позиции `$`).
- Холодный старт: сид грузит демо-новости, матчит демо-компании и ставит генерацию в очередь; воркер ждёт `/health`
  ML-сервиса и API и генерирует — первый инсайт виден сразу после входа (NFR-4).
- Роль: инсайт хранится по варианту роли; лента показывает вариант текущей роли, а пока он генерируется — вариант другой
  роли с `role_match=false`. Смена роли и правка профиля → перематчинг и генерация в очереди.

## ADR-020: Безопасность текста новостей (prompt injection)
- Дата: 2026-10-22 · Статус: принято
- Решение: тегер помечает новости флагом `suspected_prompt_injection`; Tools API отдаёт тексты как
  `{"trust": "untrusted", ...}` с обрезкой; предложения, похожие на инструкции модели, вырезаются из summary новости и
  из текста, который попадает в инсайт (`strip_injection`). Содержательные факты новости сохраняются.

## ADR-021: Дедупликация и кластеризация новостей без эмбеддингов (baseline)
- Дата: 2026-10-22 · Статус: принято (эмбеддинги добавляются в фазе 4 за той же функцией)
- Контекст: SPEC FR-N4 предполагает near-duplicate по эмбеддингам, но эмбеддинги появляются в фазе 4; сбор нужен сейчас.
- Решение (`app/domain/clustering.py`):
  - текст — пересечение основ слов заголовка и лида (лёгкое отсечение русских окончаний + обрезка до 6 символов,
    стоп-слова);
  - структура — тот же тип события, общие теги тегера (страны, сырьё, отрасли, регионы, валюты) и именованные числа
    (`key_rate=14.0`; голые проценты не учитываются);
  - `event_similarity = 0,5·текст + 0,25·тип + 0,25·теги`, событие общее при ≥ 0,5;
  - запреты: противоположные направления (рост/падение), непересекающееся сырьё или валюта (сталь vs медь),
    текстовое пересечение < 0,1;
  - почти-дубль (перепечатка) — текстовая схожесть ≥ 0,8, не сохраняется;
  - сравнение только в пределах ±72 ч от даты самой новости.
- Проверка на живых данных (587 новостей из 11 лент): верно склеены, например, Brent >113 $, Axios про ИИ-агентов,
  сюжет топливного рынка (кабмин, Новак, ФАС). Найдены и исправлены ложные срабатывания: омоним «стали»
  (глагол vs металл) в тегере, общий процент, окно на всю пачку вместо ±72 ч от новости.
- Последствия: детерминированно, без зависимостей; ML может заменить `text_similarity` на косинус эмбеддингов.

## ADR-023: Библиотеки PDF/OCR — pypdfium2 + Tesseract CLI, fpdf2 только для синтетики
- Дата: 2026-10-23 · Статус: принято
- Контекст: нужен текстовый слой и рендер страницы в 300 dpi для OCR; лицензии должны допускать закрытый код банка.
- Решение: `pypdfium2` (PDFium, Apache-2.0/BSD) — текст и рендер; OCR — `tesseract` (Apache-2.0) через CLI
  (`stdin → tsv`, уверенность по словам), `rus+eng`, `--psm 3`. Синтетические демо-PDF генерирует `fpdf2`
  (LGPL, dev-зависимость, в образ не попадает) со шрифтом Roboto (Apache-2.0, `data/reference/fonts/`).
- Альтернативы: PyMuPDF — AGPL; pdfplumber/pdfminer — нет рендера; pytesseract — лишняя обёртка над тем же CLI.
- Последствия: `tesseract-ocr` + `tesseract-ocr-rus` в образе; без бинаря OCR-страница даёт ошибку документа
  (`status=failed`, причина в `error`), документы с текстовым слоем не затронуты.

## ADR-024: Чанкинг и гибридный поиск по аналитике
- Дата: 2026-10-23 · Статус: принято
- Контекст: агенту нужны цитаты со страницей (критерии 03, 04, 10), материалы банка будут пополняться (FAQ п.42) —
  правил под конкретные файлы быть не должно.
- Решение:
  - чанкинг (`app/domain/chunking.py`): абзацы (пустые строки, иначе — эвристика коротких строк и концов
    предложений), склейка переносов, удаление колонтитулов (абзац на ≥2 и ≥50 % страниц), раздел — лид-фраза
    «Xxx: …» или короткая строка-заголовок; ~900 символов, перекрытие одним предложением, чанк не пересекает
    страницу; метаданные документа (название, дата, темы) — эвристики без привязки к файлу;
  - шум OCR: строки с уверенностью < 0,65 отбрасываются; абзацы-оси/легенды графиков (мало слов, много обрывков)
    не индексируются, обрывки графиков в начале абзаца и подписи «Источники: …» вырезаются; юридический
    дисклеймер (раздел и фразы) не индексируется; дата выпуска — из шапки, затем из имени файла (не из тела);
    темы — по плотности упоминаний (≥ 0,3 на 1000 символов);
  - хранение: `analytics_documents` (sha256, S3-ключ, метод извлечения, средняя уверенность OCR, модель
    эмбеддингов), `analytics_pages` (текст страницы — для повторной нарезки без OCR), `analytics_chunks`
    (`vector(384)` + HNSW cosine, `tsvector('russian')` как generated column + GIN);
  - поиск: вектор top-50 + полнотекстовый top-50 (OR лексем запроса, `ts_rank_cd`) → Reciprocal Rank Fusion
    (k = 60), фильтры по дате, темам, документам; в ответе `score_breakdown` (ранги и rrf), страница, метод
    извлечения и уверенность OCR;
  - результат OCR кэшируется в S3 (`ocr/<sha>/<page>.<метод>.json`) — переиндексация не повторяет OCR;
  - пользователю — presigned URL (15 мин) на PDF с `#page=N`; синтетические материалы помечаются
    «ДЕМО (синтетика)» в названии, источнике инсайта и подсказке к ссылке.
- Альтернативы: только вектор — промахи на числах и терминах («ОФЗ 26238», «14,0%»); фиксированные окна по
  символам — разрывают разделы и цитаты; внешний поисковый движок — лишний сервис.
- Последствия: качество зависит от OCR сканов (см. `docs/DATA.md`); ML может заменить эмбеддинги/реранкер за
  `EmbeddingProvider` без изменений контракта `AnalyticsHit`.

## ADR-025: Атомарная переиндексация и устойчивые ссылки на цитаты
- Дата: 2026-10-23 · Статус: принято
- Контекст: повторная обработка PDF меняла UUID всех чанков, ломая ссылки из сохранённых инсайтов;
  ошибка эмбеддингов скрывала ранее готовый документ, а параллельные загрузки могли конфликтовать.
- Решение: загрузка и переэмбеддинг используют транзакционную advisory-блокировку по SHA-256 PDF.
  Старый готовый индекс остаётся доступен до атомарной публикации нового. При неудаче повторной обработки
  сохраняются статус `ready`, прежние чанки и модель; причина последней ошибки записывается в `error`.
  Для неизменившихся `(page, chunk_index, section, text)` сохраняется UUID чанка. Пустой результат OCR
  считается ошибкой обработки. Смена векторов и метки модели выполняется одной транзакцией на документ.
- Альтернативы: удалять готовый индекс перед вычислением — теряются доступность и цитаты; глобальная
  блокировка — мешает обработке независимых PDF.
- Последствия: разные документы обрабатываются независимо; операции над одним PDF сериализованы.
  На время OCR/эмбеддингов удерживается транзакция и соединение воркера. Уже опубликованные документы
  не исчезают из поиска при сбое провайдера; ссылки на действительно изменившиеся чанки могут устареть.

## ADR-026: Проверка эмбеддингов и полнотекстовый поиск при отказе модели
- Дата: 2026-10-23 · Статус: принято
- Контекст: OpenAI-совместимый сервер может возвращать элементы не по порядку входов. Неверная длина,
  размерность, нулевые или нечисловые векторы повреждают индекс; автоматический переход `local → fake`
  нарушает правило явного выбора тестовых провайдеров.
- Решение: проверять количество, индексы, размерность и конечность реальных эмбеддингов, восстанавливать
  порядок по `index`, нормализовать перед записью. Для remote доступен `EMBEDDING_REMOTE_KEY` из env.
  Ошибка загрузки локальной модели даёт минутную паузу перед повторной попыткой. При отказе модели или
  HTTP-сервиса поиск возвращает полнотекстовые результаты с `vector_rank=null`; новые документы с
  неполученными эмбеддингами не публикуются. `fake` работает только при явном `EMBEDDING_PROVIDER=fake`.
- Последствия: неполный/повреждённый ответ не связывается с другими текстами; отказ модели не прерывает
  доступ к проиндексированным текстам. Режим виден по breakdown и событию `analytics_lexical_fallback` в логах.
  Существовавшие документы `fake-hash@1` нужно переиндексировать после подключения настоящей модели.

## ADR-027: Ограничения обработки PDF и управление процессом OCR
- Дата: 2026-10-23 · Статус: принято
- Контекст: повреждённый или слишком большой PDF не должен занимать всю память воркера;
  тайм-аут/отмена OCR должны завершать дочерний процесс, а CLI должен сообщать о частичных неудачах.
- Решение: ограничить PDF 50 МБ и 150 страницами, рендер — 25 млн пикселей на страницу
  (настройки `ANALYTICS_MAX_BYTES`, `ANALYTICS_MAX_PAGES`, `ANALYTICS_MAX_RENDER_PIXELS`). Файлы читаются
  с верхней границей до передачи парсеру; проверяется PDF-заголовок. Вызовы PDFium в одном процессе
  защищены общим mutex, поскольку библиотека не поддерживает одновременные вызовы из потоков
  ([документация](https://pypdfium2.readthedocs.io/en/stable/python_api.html#incompatibility-with-threading)).
  Bitmap, изображение и PDF-объекты закрываются явно. При тайм-ауте/отмене Tesseract выполняются kill и wait.
  Импорт каталога принимает `.pdf` без учёта регистра, продолжает обработку после ошибок отдельных файлов;
  несуществующий каталог даёт ошибку, частично неудачный импорт заканчивается кодом 1 после JSON-отчёта.
- Последствия: очень большие страницы обрабатываются с меньшим разрешением; OCR/эмбеддинги разных
  документов могут выполняться независимо, нативные операции PDFium внутри процесса сериализованы.

## ADR-028: LLM Gateway — резерв бюджета, маскирование, кэш, журнал
- Дата: 2026-10-23 · Статус: принято
- Контекст: О4 — только модели из белого списка и жёсткий дневной бюджет (~500 ₽); О6 — чувствительные данные не
  уходят во внешние модели; критерий 12 — вызовы LLM видны в трассировке. Тарифы организаторов неизвестны.
- Решение:
  - `/internal/llm/{models,budget,chat/completions}` по `contracts/llm-gateway.openapi.yaml`; доступ — run-токен
    запуска агента (`X-Run-Id` при наличии должен совпадать) или `ML_SERVICE_TOKEN`;
  - белый список — алиасы `ALLOWED_LLM_MODELS`, маппинг на ID провайдера — `LLM_MODEL_MAP`; иное → 403
    `model-not-allowed`;
  - **бюджет с резервированием**: перед вызовом под `pg_advisory_xact_lock` считается потраченное за день (Москва,
    UTC+3) плюс резервы вызовов в полёте, и вставляется строка `pending` с оценкой стоимости (вход — символы/3,
    выход — `max_tokens` или `LLM_DEFAULT_MAX_TOKENS`); после ответа резерв заменяется фактом из `usage`.
    Конкурентные вызовы не могут вместе превысить лимит; второй предохранитель — токены в сутки. Исчерпан → 429
    `budget-exhausted` + `log.error` + метрика `llm_budget_exhausted_total`; бэкенд передаёт агенту
    `options.allow_llm=false` (деградация NFR-9);
  - цены `LLM_PRICES` (₽ за 1M токенов); для моделей без тарифа — консервативные `LLM_DEFAULT_PRICE_RUB_PER_1M`
    (100/300 ₽), чтобы до получения тарифов бюджет считался с запасом (открытый вопрос);
  - маскирование до отправки и до ключа кэша: ID физлиц, e-mail, телефоны, отдельно стоящие числа из 10–20 цифр
    (ИНН, ОГРН, счета); суммы с разделителями и десятичные числа не трогаются;
  - кэш ответов на запросы с `temperature=0` без стриминга (`core.llm_cache`, TTL `LLM_CACHE_TTL_H`): попадание —
    стоимость 0, `X-Cache: hit`;
  - журнал `core.llm_usage` — каждый вызов (ok, cached, refused, error) с моделью, целью (`X-Purpose`), токенами, ₽,
    латентностью, run_id и маскированным превью ≤ 500 символов; трассировка инсайта показывает `llm_calls`,
    `GET /api/v1/admin/llm-usage` — сводка;
  - провайдер — OpenAI-совместимый HTTP (повтор на 429/5xx и сетевые ошибки, таймаут → 504, ошибка → 502);
    `LLM_PROVIDER=fake` — детерминированные ответы для тестов и e2e (по умолчанию выключен); стриминг SSE с учётом `usage`.
- Альтернативы: учёт после ответа без резерва — параллельные запросы перерасходуют бюджет; счётчик в Redis — бюджет
  должен переживать перезапуски и сходиться с журналом, а источник правды для `llm_usage` — Postgres.
- Последствия: оценка завышает стоимость (резерв по `max_tokens`), поэтому при почти исчерпанном бюджете последний
  вызов может быть отклонён, хотя фактически уложился бы. Это сознательный запас.

## ADR-029: Матчинг по всей базе — предфильтр по инвертированному индексу
- Дата: 2026-10-23 · Статус: принято
- Контекст: FR-M1, NFR-3 (событие по всей базе < 5 с). Раньше событие скорилось только против компаний с
  пользователями.
- Решение:
  - `affected_companies` — один SQL над денормализованными колонками `company_context` (GIN `&&` по отраслевым
    тегам, тегам контрагентов, странам ВЭД, сырью; регион; флаги чувствительности; граф для упомянутых компаний;
    данные анкеты): надмножество компаний, которые скорер может оценить ≥ `MATCH_MIN_SCORE`. Свойство проверяет
    integration-тест на всей синтетике: каждая пара со score ≥ порога есть в предфильтре;
  - `MATCH_SCOPE=users` (по умолчанию) — кандидаты для компаний с пользователями, `all` — для всей клиентской базы
    (у компаний без пользователей роль `owner`); генерация ставится в очередь только для компаний с пользователями;
  - `company_context.scoring_features` — готовый компактный профиль скорера (`{"v": 1, ...}`, ≈0,4 КБ вместо ≈6 КБ
    полного контекста): считается вместе с контекстом, матчинг восстанавливает профиль без разбора признаков.
    Строки без `"v"` (до этой версии) читаются как признаки — совместимость сохранена;
  - логика скорера не меняется (зона ML): предфильтр подстраивается под него. Скорер видит отрасль контрагентов
    при любой доле, поэтому в индекс добавлена колонка `counterparty_tags_any` (все отрасли с долей > 0, GIN), а
    `counterparty_tags` (доля ≥ 5 %) остаётся для прочих потребителей. Единственный компонент без признака —
    запасной вариант для ставки 0,2 — сам по себе не достигает порога (0,95 · 0,2 < 0,2); если ML понизит
    `MATCH_MIN_SCORE` ниже этой величины, `match_events` откажется работать, а не потеряет кандидатов;
  - после миграции 0006 контексты нужно пересобрать (`scripts/ingest.py companies`), иначе новые колонки пусты.
- Результат на данных организаторов (41 968 клиентов CLIENT, 15 событий демо-ленты) измерен с прежним
  индексом `counterparty_tags`: худшее событие 3,0 с (до компактных признаков — 5,96 с). С `counterparty_tags_any`
  предфильтр шире: худшее событие 5,0 с (ставка, 28 815 кандидатов). После перехода на готовый компактный профиль
  загрузка профилей — 1,8 с вместо 3,6 с, худшее событие — 4,1 с.
- Замечание для ML: на событии «налоговое регулирование» скорер даёт ~0,4 компании с 0,35 % платежей в отрасли
  (буст регулирования включается от любого ненулевого компонента) — кандидат на пересмотр правил в зоне ML.
- Последствия: новый компонент скорера, не выразимый колонками индекса, требует расширить предфильтр — иначе
  integration-тест надмножества упадёт.

## ADR-030: Доставка по CJM — уведомления, дайджест, вопросы, метрики
- Дата: 2026-10-23 · Статус: принято
- Контекст: CJM финансового директора (8 этапов, north star «доля сессий с полезным инсайтом и понятным
  следующим шагом»). Генерация и тексты ответов — зона ML; бэкенд — доставка, проверка, учёт.
- Решение:
  - **уведомления** — `core.notifications` с `dedup_key` на пользователя: срочный инсайт или инсайт с влиянием
    high/critical (по событию, а не по варианту роли), дайджест дня/недели (планировщик), смена статуса заявки.
    SSE-поток опрашивает БД раз в `NOTIFICATIONS_POLL_S` и живёт до `max_s` (по умолчанию 300 с), клиент
    переподключается с `Last-Event-ID`; без брокера сообщений и работает с любым числом процессов API;
  - **дайджест** — детерминированная сводка из ленты за период (счётчики, топ-5, риски, возможности, по одному
    следующему шагу из самих инсайтов); текст не генерируется;
  - **вопросы** — прокси SSE `/v1/chat` агента (ML или ml-stub) с run-токеном Tools API; вопрос — запуск агента
    (`agent_runs.kind=chat`) с трассировкой; `done` агента придерживается до проверки `ChatFinal` (схема +
    источники у fact/bank_analytics), дисклеймер добавляет бэкенд; ветка хранится в `core.qa_messages`;
  - **«наблюдать»** — состояние `watch` (сохранить + событие), без заявки в CRM; **отзыв** возвращает, что сделано
    (при «нерелевантно» инсайт скрывается сразу); **заявки** — `GET /me/requests`, статусы мок-CRM меняет админ;
  - **карточка** — `why_for_you` (первая причина из инсайта), `priority_reasons` (подписи компонентов релевантности,
    без пересчёта), `state.updated` (инсайт перегенерирован после просмотра);
  - **метрики** — лог `core.user_actions` + события UI (`POST /events`, белый список), сессия — 30 минут,
    определения в `docs/METRICS.md`; `GET /admin/metrics` и снимки `core.metrics_daily`.
- Альтернативы: Redis pub/sub или LISTEN/NOTIFY для уведомлений — быстрее, но сложнее переподключение и
  тестирование; опроса раз в 2 с достаточно для «срочного» на масштабе прототипа. Токен в query для EventSource —
  попадает в логи прокси.
- Последствия: задержка уведомления до 2 с; метрика этапа 04 не считается из логов (опрос и экспертиза).

## ADR-031: Ручной ввод новостей и e2e без внешней сети
- Дата: 2026-10-23 · Статус: принято
- Контекст: сценарии №9 («новая срочная новость → SSE») и №12 («неизвестная новость») требуют подать новость во
  время теста; №11 — показать переход на резервный источник. e2e не должен ходить в интернет.
- Решение:
  - источник `manual` (коннектор `ManualConnector`, абсолютные даты) и `POST /api/v1/admin/news` (роль admin, до

    prompt injection, матчинг, очередь генерации, уведомления — тот же путь, что у RSS. Источник не опрашивается

    исчерпать бюджет в тесте.
- Альтернативы: подменять файл демо-ленты в контейнере — нужен общий том и гонки с планировщиком; ждать
  планировщика — минуты на тест.
- Последствия: ручные новости видны в `/admin/sources/health` как источник `manual`; их нельзя отличить от
  опубликованных по содержанию — поэтому только для роли admin.

## ADR-032: Compose по частям, отдельные сервисы Dokploy и автодеплой из CI
- Дата: 2026-10-23 · Статус: принято
- Контекст: в репозитории три части (`backend/`, `ml/`, `frontend/`) от разных команд, а compose был один в корне.
  Нужен и общий запуск одной командой (требование кейса), и деплой каждой части отдельно. Деплой в Dokploy не
  срабатывал: CI ничего не вызывал, а Dokploy ждал push в другую ветку. Схема повторяет проверенную в соседнем
  проекте команды (VTB-Hack).
- Решение:
  - у каждой части свой compose в её папке: `<часть>/docker-compose.yml` — сервис Dokploy (Compose Path), без
    портов на хосте; `<часть>/docker-compose.override.yml` — порты для локального запуска. У бэкенда ещё оверлей e2e
    `backend/docker-compose.test.yml`; его образ собирается из корня (`context: ..`), потому что ему нужны `contracts/`;
  - корневой `docker-compose.yml` только подключает части через `include` (файл части + override); `make up` и
    `docker compose up -d --build` из корня работают как раньше. В Dokploy корневой файл не используется;
  - как в VTB-Hack, значения по умолчанию в файлах частей — для Dokploy: сеть `shared` — внешняя `dokploy-network`,
    `BACKEND_ALIAS` обязателен; в Dokploy остаются только алиас и секреты. Локальный режим включает корневой запуск:
    `.env.example` (env-файл `include`) задаёт `SHARED_NETWORK_EXTERNAL=false` и своё имя сети, `make e2e` — свои.
    Имена в общей сети: `BACKEND_ALIAS` (api — для фронтенда, ML и Traefik), `ML_ALIAS` (ML-сервис — для
    `ML_SERVICE_URL`). У prod и dev они разные, иначе окружения на одном сервере попадут друг в друга. Каждая часть
    объявляет сеть `shared` одним и тем же блоком. Запуск части без корня (`cd backend && docker compose up`) не
    поддерживается;
  - фронтенд (nginx) берёт адрес API из `BACKEND_UPSTREAM` (шаблон конфига образа nginx) и резолвит его при запросе:
    поднимается раньше бэкенда и не зависит от имени сервиса `api`, которое в общей сети есть у каждого окружения;
  - окружения: prod — ветка `main`, dev — ветка `dev`; в каждом свои сервисы Dokploy и GitHub Environment;
  - CI: задание `frontend` собирает образ фронтенда (тот же, что Dokploy), e2e проверяет compose-файлы частей в
    режиме Dokploy; `deploy` — после зелёных integration, e2e и frontend, на push; матрица backend, ml, frontend —
    часть без compose-файла пропускается; вебхук — секрет окружения `DOKPLOY_WEBHOOK_<ЧАСТЬ>`, нет секрета — ошибка;
    успех — только HTTP 200 (на несовпадение ветки Dokploy отвечает 301).
- Альтернативы: один общий compose — команды правят общий файл и конфликтуют, а Dokploy поднимает всё одним сервисом;
  автодеплой Dokploy по вебхуку GitHub — деплоит и красные коммиты, молча ломается при смене ветки или имени репозитория.
- Последствия: у сервисов Dokploy включён Auto Deploy (без него вебхук отклоняется), источник — провайдер Git, а не
  GitHub App (иначе Dokploy деплоит на push сам, до тестов). ML-сервис (`ml/`) подключён так же: свой compose,
  алиас `ML_ALIAS`, секрет `DOKPLOY_WEBHOOK_ML`; бэкенд передаёт ему адреса Tools API и Gateway по `BACKEND_ALIAS`.
  Новая часть подключается строкой `include` в корне, сервисом Dokploy и секретом; правки CI не нужны.

## ADR-033: PDF аналитики отдаёт API по ссылке с токеном, а не presigned S3
- Дата: 2026-10-23 · Статус: принято
- Контекст: ссылка на страницу PDF (FR-A6) была presigned URL MinIO с хостом `S3_PUBLIC_ENDPOINT_URL`
  (`http://localhost:9000`). На сервере (Dokploy, ADR-032) MinIO наружу не открыт: ссылка из карточки инсайта
  у пользователя не открывалась. Открыть MinIO — отдельный домен, TLS и ещё один публичный сервис с хранилищем.
- Решение: `download` и `source-click` возвращают относительную ссылку
  `/api/v1/analytics/documents/{id}/file?token=…#page=N`. Токен — JWT типа `doc` на один документ, 15 минут
  (браузер открывает PDF в новой вкладке без заголовка Authorization). `GET …/file` проверяет токен и потоком
  отдаёт PDF из S3 (`application/pdf`, `inline`). Ссылка работает везде, где работает API, — и через nginx
  фронтенда на том же домене. `S3_PUBLIC_ENDPOINT_URL` и публичный S3-клиент удалены.
- Альтернативы: публичный домен MinIO — лишняя поверхность атаки и настройка на каждом стенде; проксировать
  MinIO в nginx фронтенда — подпись presigned URL завязана на хост, ломается за прокси.
- Последствия: трафик PDF идёт через api (файлы до 50 МБ, потоком по 64 КБ); токен в адресе может попасть в журнал
  прокси — поэтому он короткий и открывает только один документ.

## ADR-034: Операционные алерты — одна периодическая проверка, Telegram или лог
- Дата: 2026-10-24 · Статус: принято
- Контекст: о падении источника, исчерпании бюджета LLM, массовых отклонениях инсайтов, зависших запусках и
  недоступном ML-сервисе узнавали только из логов или админки. На демо и на сервере это видно слишком поздно.
- Решение: задача `alerts.check` (планировщик, раз в 5 минут) оценивает состояние по БД и доступности ML и
  отправляет каждое активное условие не чаще раза за `ALERT_COOLDOWN_MIN` (ключ в Redis на условие; при ошибке
  отправки ключ снимается — повтор на следующей проверке). Канал — `ALERTS_PROVIDER`: `log` (по умолчанию) или
  `telegram` (Bot API, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`); без настроек бота — лог. `GET /admin/alerts`
  показывает те же условия сейчас. Пороги: бюджет ≥ 80 % — предупреждение, исчерпан — критично; отклонено
  ≥ `ALERT_REJECT_RATIO` инсайтов за час (минимум 5); зависшие запуски — как в мониторе генерации.
- Альтернативы: хуки в каждом конвейере — разбросанная логика и дубли при повторах; Prometheus Alertmanager —
  ещё один сервис на стенде хакатона.
- Последствия: задержка до 5 минут; токен бота — секрет (в ошибки и логи не попадает: URL с токеном не логируется).

## ADR-035: Доля дневного бюджета LLM на вопросы к аналитике
- Дата: 2026-10-24 · Статус: принято
- Контекст: бюджет LLM общий на день (ADR-028, 450 ₽). Вопросы пользователей (чат, ≈0,4 ₽) приходят в любой
  момент; активный пользователь на демо мог исчерпать бюджет, и предгенерация ленты новых событий пошла бы без LLM.
- Решение: вызовы Gateway из запусков вида `qa` (`agent_runs.kind`, определяется по run-токену, а не по заголовку
  `X-Purpose`, который ставит сам агент) резервируют стоимость в пределах `LLM_CHAT_BUDGET_SHARE` дневного бюджета
  (по умолчанию 30 %); остальное гарантированно остаётся генерации. Проверка — под той же блокировкой бюджета.
  Отказ — тот же `429 budget-exhausted` (контракт не меняется: агент уже переключается на правила), в `detail`
  указано, что исчерпана доля вопросов. `GET /admin/llm-usage` показывает `chat_limit_rub` и `chat_spent_rub`.
- Альтернативы: отдельный бюджет генерации — генерация и так ограничена общим лимитом; доверять `X-Purpose` —
  агент мог бы обойти долю.
- Последствия: при исчерпанной доле вопросы отвечаются без LLM (правила агента), лента продолжает генерироваться.

## ADR-036: Источники новостей настраивает админ; сборщик ходит только в публичный интернет
- Дата: 2026-10-24 · Статус: принято
- Контекст: список источников жил только в `news_sources.json` — добавить ленту (например, зарубежную) или
  выключить шумную можно было только правкой репозитория и деплоем. Синхронизация каталога при каждом опросе
  перезаписывала `enabled`. Если адрес задаёт человек, сборщик становится способом сходить во внутреннюю сеть
  (minio, api, сервис метаданных облака) — SSRF.
- Решение:
  - `core.sources.origin` (`catalog` — из файла, `admin` — добавлен админом) и `disabled_by_admin`. Синхронизация
    каталога включает источник, только если его не выключил админ; источники админа в файле не описаны и
    синхронизацией не меняются (кроме общего `NEWS_LIVE_SOURCES_ENABLED`);
  - админ-API `/admin/sources`: список; `check` — проверка ленты без сохранения (доступность, robots.txt, разбор
    RSS/Atom, последние новости); добавление RSS/Atom только после успешной проверки, сразу опрос в очереди;
    `PATCH` — включить/выключить любой, у своих — ещё имя, приоритет, резерв, темы; удаление — только своих и
    только пока по ним нет новостей (иначе выключить: новости ссылаются на источник);
  - сборщик (`NEWS_PUBLIC_HOSTS_ONLY`, по умолчанию включено): только http(s), порты 80/443, без логина в URL;
    перед каждым запросом, включая редиректы и robots.txt, все адреса хоста должны быть публичными. Вид
    `fixture` (локальный файл) админу недоступен.
- Альтернативы: править `news_sources.json` через API — файл в образе, изменения пропадут при деплое; список
  разрешённых доменов — ограничивает выбор источников, а SSRF всё равно надо закрывать по адресам.
- Последствия: проверка по DNS до соединения не закрывает DNS rebinding полностью (между проверкой и
  подключением адрес может смениться) — приемлемо: источники добавляет только админ. Тегер пока понимает
  русский текст: англоязычная лента собирается, но её новости хуже матчатся с компаниями (BACKLOG).


## ADR-037: Соответствие законодательству РФ — правила для новостей, инсайтов и ответов
- Дата: 2026-10-24 · Статус: принято
- Контекст: сервис банка собирает новости, в том числе зарубежные, и публикует выводы. Распространение
  дискредитирующих ВС РФ материалов, призывов к санкциям против России, к экстремизму или терроризму, а также
  материалов нежелательных организаций — нарушение (ст. 20.3.3 КоАП; ст. 207.3, 280.3, 284.2, 205.2, 280 УК РФ).
- Решение (`app/domain/compliance.py`, детерминированные правила по предложениям):
  - **новости** (сбор, ручной ввод, ссылки пользователей): блокируется только дискредитация ВС РФ — обвинения,
    направленные на Россию («российская агрессия», «вторжение России», «Russia's invasion»), или термин о
    российских войсках рядом с обвинением в преступлениях. Сообщения о чужих действиях (санкции ЕС, уголовное
    дело о призывах) — обычная новость и проходят. Заблокированная новость не сохраняется и не становится
    событием (`n_blocked` в отчёте опроса, предупреждение в логе); сырьё остаётся в S3 для аудита;
  - **собственные выводы** (инсайты — валидатор, ответы чата — проверка ответа): все три правила; нарушение —
    отклонение с причиной `compliance_*` и статьёй закона, видно ML-команде в `insights_rejected`;
  - **реестр** `data/reference/compliance_registry.json` (нежелательные организации, иноагенты): новости с этих
    доменов не принимаются, источник с таким адресом не добавить. Список надо сверять с официальными реестрами
    (Генпрокуратура, Минюст, Роскомнадзор) перед релизом.
- Альтернативы: LLM-модерация — точнее по смыслу, но это зона ML и бюджет; может дополнить правила (ML-сервис
  получает отказы валидатора). Блокировать по словам «армия», «санкции», «агрессия» без контекста — заблокировало
  бы основную деловую повестку.
- Последствия: правила — страховочная сетка, а не юридическая экспертиза: возможны пропуски перефразировок и
  редкие ложные срабатывания; примеры обоих направлений — в `tests/unit/test_compliance.py`.

## ADR-038: Пользователь присылает ссылку или текст новости
- Дата: 2026-10-24 · Статус: принято
- Контекст: клиент видит новость, которой нет в наших источниках (отраслевой сайт, сообщение партнёра), и хочет
  понять, что она значит для его компании. Новость от пользователя не проверена: она не должна попадать в ленты
  других клиентов.
- Решение: `POST /api/v1/news/submit` (`company_id` + `url`, либо `title` + `text`):
  - ссылка открывается вежливо (robots.txt, только публичные адреса, ADR-036), из HTML выделяются заголовок,
    текст, дата и издатель (`app/integrations/news/article.py`). Если сайт недоступен с сервера — ответ
    `unavailable` «Ресурс сейчас недоступен для просмотра» с причиной, а не ошибка; лента вместо статьи —
    `not_article` (её может добавить админ как источник);
  - сайт из реестра и текст, нарушающий законодательство РФ, — `blocked` со статьёй закона (ADR-037);
  - дальше — общий конвейер (источник `user`): сырьё в S3, дедупликация, событие. Событие, известное только из
    присланных пользователями материалов, приватно: `events.private_company_ids` — компании этих пользователей;
    матчинг для других компаний его не видит, Tools API не отдаёт такие новости агенту чужой компании. Когда ту же
    новость приносит настоящий источник, событие становится общим;
  - матчинг — только для компании пользователя; значимое событие сразу ставится в генерацию, инсайт приходит в
    ленту и уведомлением. Не больше 30 присланных новостей в сутки на пользователя.
- Альтернативы: проверять новость у админа перед обработкой — медленно для клиента; обрабатывать как обычную
  новость — непроверенный текст одного клиента попал бы к другим.
- Последствия: инсайт по присланной новости строит агент так же, как по любой другой; в источнике видно издателя
  или «Текст от пользователя».
