# ML: подключение, проверка и следующие шаги

Состояние документа: 26.10.2026. ML-сервис уже включён в общий стек как генератор по умолчанию
(`INSIGHT_GENERATOR=remote`, `ML_SERVICE_URL=http://ml:8200`). Адрес шлюза организаторов, идентификаторы
шести разрешённых моделей и ориентировочные тарифы заданы в бэкенде. Неизвестный `LLM_BASE_URL` больше
не является блокером подключения: для LLM нужен действующий `LLM_API_KEY` в окружении бэкенда.

Без LLM агент использует `rules@1`; при отсутствии семантической модели ранкер переходит с `ml-ranker@2`
на правила `ml-ranker@1`. Это разные механизмы деградации. Состояние конкретного запуска проверяют
по трассе, `models_used` и `/v1/info`, а не по тому, что в ленте появилась карточка.

Полная документация проекта — [`../docs/PROJECT_GUIDE.md`](../docs/PROJECT_GUIDE.md), протокол интеграции —
[`../docs/INTEGRATION_ML.md`](../docs/INTEGRATION_ML.md), эксплуатация — [`../docs/RUNBOOK.md`](../docs/RUNBOOK.md).
Текущий цикл исправлений интеграции ограничен кодом бэкенда; ML-реализация и промпты остаются ответственностью
ML-команды. Общие схемы и форматы не следует менять без согласованного изменения контракта.

## 1. Подключить LLM к работающему стеку

1. В корневом `.env` или секретах Backend-сервиса Dokploy задать:

   ```dotenv
   LLM_API_KEY=<ключ команды>
   LLM_DAILY_BUDGET_RUB=450
   ```

   Ключ не передаётся в ML-сервис. Адрес по умолчанию — `https://api.alfahack-gateway26.ru/v1`;
   `LLM_BASE_URL`, `LLM_MODEL_MAP`, `LLM_PRICES` нужны только для переопределения значений из
   `backend/app/core/config.py`. Если провайдер недоступен из сети сервера, используется `LLM_PROXY_URL`.
2. Проверить, что у бэкенда и ML совпадает `ML_SERVICE_TOKEN`, а передаваемый агенту `INTERNAL_API_URL`
   доступен из контейнера ML. При отдельном деплое адрес определяется через `BACKEND_ALIAS`.
3. Применить окружение: `docker compose up -d --build` из корня; в Dokploy пересоздать Backend-сервис.
4. Проверить `/api/v1/admin/llm-usage`: ошибки и расходы; `/api/v1/admin/llm-provider`: доступный остаток
   у провайдера. Доступ к этим запросам требует учётку администратора.
5. Сделать ограниченный smoke-прогон через Gateway: `make smoke-live` из корня. Для локального скрипта
   экспортировать `ML_SERVICE_TOKEN`, совпадающий со стендом, и при необходимости `LIVE_API_URL`.
   `uv` запускается из `backend/`: корневой `.env`, который использует Docker Compose, автоматически
   не становится окружением локального Python-процесса. Проверка требует запущенный API, интернет
   и расходует бюджет LLM; внешнего провайдера напрямую она не вызывает.

Включённый ключ не гарантирует LLM для каждой карточки: агент учитывает релевантность, остаток времени,
бюджет и настройки `ML_LLM_*`. Подтверждение LLM-генерации — успешный вызов в трассе и учёте расхода.

## 2. Бюджет и настройки агента

| Ограничение | Значение по умолчанию |
|---|---|
| Денежный лимит Gateway | `LLM_DAILY_BUDGET_RUB=450` ₽ |
| Лимит токенов | `LLM_DAILY_TOKEN_LIMIT=3000000` |
| Доля дня на вопросы | `LLM_CHAT_BUDGET_SHARE=0.3` |
| Начало бюджетного дня | 03:00 МСК, как у провайдера |
| Порог LLM-черновика | `ML_LLM_MIN_SCORE=0.5`, ниже — `rules@1` |
| Раунды исправления после критика | `ML_MAX_ITERATIONS=1` |
| Планировщик / критик | `ML_LLM_PLANNER=true`, `ML_LLM_CRITIC=true` |

При `temperature=0` и без streaming Gateway может вернуть кэшированный ответ (`X-Cache: hit`) без нового
вызова провайдера. При исчерпании бюджета Gateway возвращает 429; агент продолжает по правилам.
Лимит `ML_SKIP_THRESHOLD=0.35` относится к отбору правилами; у обученного ранкера есть собственный порог
и обработка известных размеченных пар.

Если расход слишком велик, можно повысить `ML_LLM_MIN_SCORE`, отключить LLM-планировщик или критика.
Процент экономии и цена инсайта зависят от длины контекста, модели, повторов и кэша; оценивать их нужно
по фактическому `/admin/llm-usage`, а не по старым оценкам стоимости. Массовые LLM-eval не входят
в приёмочный smoke-тест.

## 3. Проверить backend ↔ настоящий ML

Из корня репозитория:

```bash
make check
make e2e
make e2e-ml
```

`make check` проверяет бэкенд, `make e2e` — полный API-сценарий с `ml-stub`. Отдельный `make e2e-ml`
поднимает настоящий ML-сервис и проверяет HTTP-связку с бэкендом: очередь генерации, Tools API,
валидатор, ленту, трассу, чат SSE, score и авторизацию. В этом прогоне LLM и семантические модели
отключены; он не оценивает их качество и не расходует внешний бюджет.

Проверки ML отдельно, из `ml/`:

```bash
uv sync --frozen
uv run ruff check alfa_ml tests eval scripts
uv run ruff format --check alfa_ml tests eval scripts
uv run mypy
uv run pytest -q
```

Для живой приёмки проверить несколько релевантных карточек и вопросов, включая разные компании:

- Компания и роль меняют подборку и объяснение; в `why_it_matters` есть реальные признаки.
- Трасса содержит успешные `llm_call` там, где ожидается LLM, и показывает причины деградации.
- Факты и позиция банка имеют источники; цитата открывается на нужной странице PDF.
- При отсутствии подходящего документа позиция банка не выдумывается.
- Чат завершается `done` с проверенным ответом; `error` обрабатывается клиентом.
- В логах `semantic_ready`, если ожидается `ml-ranker@2`; `semantic_unavailable` означает fallback.

Подключение ключа и наличие тестов не подтверждают, что эти проверки выполнены на конкретном dev/prod-стенде.

## 4. Оценка качества и работа с регрессиями

Существующие результаты: [`reports/eval.md`](reports/eval.md),
[`reports/heldout.md`](reports/heldout.md), [`reports/heldout_set2.md`](reports/heldout_set2.md),
[`reports/live_feed.md`](reports/live_feed.md), [`reports/ranker2.md`](reports/ranker2.md),
[`reports/ranker2_blind_set4.md`](reports/ranker2_blind_set4.md),
[`reports/ranker2_blind_set5.md`](reports/ranker2_blind_set5.md),
[`reports/real_profiles.md`](reports/real_profiles.md), [`reports/real_analytics.md`](reports/real_analytics.md).
Это разные наборы и даты измерений; процент прохождения валидатора не доказывает истинность текста
или качество отбора на всех новых новостях.

Офлайн-прогон без LLM, из `ml/`:

```bash
uv run python -m eval.run_eval
```

Следующая оценка должна использовать новости и разметку, отложенные до любых изменений модели.
После использования набора для исправлений его больше нельзя считать независимой слепой проверкой.
Результат сохраняется с датой, версией кода, режимом моделей и описанием данных.

Исторические ошибки живого потока — омонимы, рубрики вместо заголовков, трансляции, дубли и лишние
сырьевые теги — перечислены в `reports/live_feed.md`. Часть правил бэкенда с тех пор изменилась;
старый отчёт не является списком подтверждённых текущих дефектов. Для каждого нового случая нужно
сохранить заголовок/лид, ожидаемое решение и минимальную регрессию в тестах бэкенда либо передать
ML-команде, если проблема в её логике.

## 5. Дальнейшее развитие

- Пополнять независимую разметку реальными ошибками и проверять recall важных событий вместе с долей шума.
- Согласовать переобучение `ml-ranker@2` и обновление памяти разметки с ML-командой.
- Измерить Recall@5 RAG на бизнес-вопросах перед добавлением cross-encoder или VLM.
- Проверить полный пользовательский сценарий после деплоя и отдельно при отказе LLM.
- Сохранять совместимость контрактов: изменения описывать в ADR и `contracts/CHANGELOG.md`.
