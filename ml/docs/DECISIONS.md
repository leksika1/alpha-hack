# Решения ML-команды (ADR-ML)

Формат: контекст → решение → альтернативы → последствия. Общие ADR проекта — `docs/DECISIONS.md`.

## ADR-ML-001. Свой оркестратор агента вместо LangGraph

**Контекст.** Нужна агентная логика (план, инструменты, самопроверка, повторы) с полной трассировкой в формате
бэкенда (`log_step`) и жёстким лимитом 60 с на запуск.
**Решение.** Небольшой явный граф на Python (`agent/runner.py`): шаги и переходы видны в коде, каждый шаг пишет
`log_step`, бюджет времени проверяется перед каждым LLM-вызовом.
**Альтернативы.** LangGraph — удобен для сложных графов, но добавляет зависимость, собственную трассировку
и неявное состояние; для 6–8 шагов выигрыша нет. Свободный ReAct с tool calling — дороже по токенам,
непредсказуемая длина, у части разрешённых моделей нестабильный tool calling.
**Последствия.** Добавить шаг — функция + запись в трассировку; граф описан в `docs/ARCHITECTURE.md`.

## ADR-ML-002. «Классификатор решает, LLM объясняет»

**Контекст.** Главные риски кейса (FAQ п.47): пропуск важного события, нерелевантный контент, необоснованная
интерпретация. Бюджет — 500 ₽ на всё.
**Решение.** Подверженность компании событию, решение о показе, шкала влияния и релевантность считаются
детерминированно по признакам компании (`profile.py`, `ranker.py`, `impact.py`). LLM пишет интерпретацию
только для уже отобранных пар и может сдвинуть влияние не более чем на 15 пунктов.
**Альтернативы.** LLM-скоринг каждой пары: 41 968 клиентов × события — недопустимо по бюджету и задержке.
Дистилляция LLM в малый классификатор (идея команды 6 PROD-2026) — нужен размеченный LLM датасет; в бэклоге.
**Последствия.** Лента работает без LLM; «почему вам это показано» всегда объяснимо признаками.

## ADR-ML-003. Сборщик владеет фактами контракта

**Решение.** LLM возвращает компактный JSON со ссылками на ID источников и пути признаков; инсайт по
`insight.schema.json` собирает код. Несуществующие ссылки удаляются, `bank_analytics` без фрагмента аналитики →
`model_inference`, `fact` без источника → `model_inference`, цитата банка сверяется с текстом фрагмента,
количественные оценки — только детерминированные (`interest_cost_delta_per_100m`, `counterparty_share_affected`,
`counterparty_hhi`, `fx_countries_affected`, `key_rate_level`).
**Последствия.** Доля инсайтов, отклонённых валидатором бэкенда, — 0% на офлайн-наборе; галлюцинированные числа
и «мнения банка» не доходят до пользователя.

## ADR-ML-004. Маршрутизация моделей и бюджет

**Решение.** Планировщик — Gemma 4 26B A4B (350 токенов ответа), аналитик и чат — Qwen3.6 35B A3B (2200),
критик — GLM-5.3-Flash (700): критик другой модели снижает «самоодобрение». `temperature=0` → кэш Gateway.
Замер промптов на тестовых событиях: планировщик ~1,4 тыс. входных токенов, аналитик ~3 тыс., критик ~3 тыс.
Без раунда исправления ≈ 7,5 тыс. входных и ~2,2 тыс. выходных токенов на инсайт, с одним раундом ≈ 11 / 3,7 тыс.
При консервативной цене Gateway (100/300 ₽ за 1M) это ≈ 1,4–2,2 ₽ на инсайт → 200–300 инсайтов в день при лимите
450 ₽; ответ в чате ≈ 0,4 ₽. Предгенерация идёт только для пар, прошедших порог показа (ADR-ML-005).
Модели меняются переменными `ML_MODEL_*` без кода. После получения ключа — сравнение моделей на `eval/`.
**Альтернативы.** Kimi-K2.6 / DeepSeek-V4.1-Flash как аналитик — кандидаты на сравнение по качеству русского и JSON.

## ADR-ML-005. Калибровка ранжирования (ml-ranker@1)

**Контекст.** EDA: кредит/лизинг у 32% клиентов, ВЭД у 13%, у 72% один контрагент > 30% оборота. Baseline бэкенда
даёт вклад контрагента `min(1, 2·доля)` и пропускает в ленту события через контрагентов с долей 0,35%
(BACKLOG бэкенда).
**Решение.** (1) доля контрагентов < 1% — не связь, насыщение на 25%; (2) эффект через контрагентов — второго
порядка, коэффициент 0,6; для ценовых событий по отрасли покупателей ещё ×0,5; (3) страна ВЭД важна для
событий курса, санкций и логистики, для прочих — только вместе с собственной подверженностью; валюта события
сопоставляется с валютами стран ВЭД; (4) «оптовые цены» не делают событие отраслевым (`wholesale` — общий тег);
(5) регион сам по себе — фон; (6) сила события и близость влияния из шкалы v1; (7) порог показа 0,35.
**Результат** (`reports/eval.md`): доля нерелевантного в ленте 0,51 → 0,22, все важные события сохранены
(recall 1,0); nDCG@5 CFO 0,91 → 0,92, CEO 0,76 → 0,88. Порог подбирался на этом же наборе; отложенная проверка — ADR-ML-009 и `reports/heldout.md`.

## ADR-ML-006. Модель эмбеддингов для RAG бэкенда

**Решение.** `EMBEDDING_PROVIDER=local`, `EMBEDDING_MODEL=sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
(fastembed, ONNX, 384 измерения).
**Почему.** Размерность 384 уже заложена в схеме (`vector(384)`) — без миграции и переиндексации; модель
мультиязычная, без префиксов `query:`/`passage:` (бэкенд их не добавляет, а E5 без них теряет качество); на
проверочном прогоне бэкенда (8 бизнес-запросов по 9 PDF) первый результат из профильного документа во всех
случаях; работает на CPU. Гибридный поиск (BM25 + вектор + RRF) компенсирует слабости малой модели.
**Альтернативы.** `multilingual-e5-large`/`bge-m3` (1024) — лучше на русском, но миграция `vector(1024)`, префиксы
и ×5 по памяти; рассмотреть после замера Recall@5 на размеченных вопросах к аналитике.

## ADR-ML-007. Деградация вместо ошибок

**Решение.** Любой сбой LLM (нет ключа, 429 бюджета, 5xx, тайм-аут, невалидный JSON дважды подряд) переводит
запуск на rules@1; после двух неудач LLM в запуске больше не вызывается (не тратим бюджет и время). Инструмент
Tools API, кроме контекста компании и события, может упасть без провала запуска. Блокирующие ошибки
самопроверки после всех попыток → rules@1; `failed` только если и он невалиден.

Дополнение (dev-стенд, 24.10): провайдер подвисал, и каждая пара ждала таймаута LLM — перегенерация сотен пар шла
бы часами. Общий для процесса предохранитель (`llm.py`): после 3 подряд сбоев транспорта/5xx LLM не вызывается
5 минут (ответы rules@1, в трассе `circuit_open`), затем снова пробуется.

## ADR-ML-008. Защита дневного бюджета (500 ₽)

**Решение.** LLM вызывается только для пар с предварительной релевантностью ≥ `ML_LLM_MIN_SCORE` (0,5): важные
события пишет LLM, фоновые — `rules@1` без затрат. Раунд исправления после критика — один (`ML_MAX_ITERATIONS=1`).
Каждое отключение LLM видно в трассе (`llm_budget_guard`). Плюс жёсткий стоп Gateway (450 ₽) и кэш при `temperature=0`.
**Последствия.** ≈ 1,4–1,8 ₽ на LLM-инсайт; переключатели экономии — `ml/NEXT_STEPS.md` §2.

## ADR-ML-009. Нормализация события на стороне ML и правила цитирования аналитики

**Контекст.** Отложенная оценка на реальных новостях (`reports/heldout.md`) и прогон реальных PDF через OCR
(`reports/real_analytics.md`) показали: теги бэкенда описывают направление новости, а не валюты («рубль вырос» →
`CNY, up`); валюта события (EUR) делала любую европейскую новость «связанной с ВЭД»; новости об ипотеке без тега
стройки не доходили до застройщиков; склейка двух предложений чанка ломала дословную цитату банка.
**Решение.** `profile.normalize_event` (копия события, бэкенд не меняется): направление FX-события — про иностранную
валюту; «ипотека» → `real_estate/construction/developer`. Валюта события — связь с ВЭД только для FX/санкций/логистики;
отраслевая новость о другой стране без ВЭД с ней — косвенная (0,4). Сторона рынка компании (продавец/покупатель)
определяется по ОКВЭД (`rules.market_side`). Цитата банка — одно непрерывное предложение без обрезки; предложение
должно делить ≥ 2 содержательных стема с заголовком; материалы старше года помечаются датой.
**Альтернативы.** Исправлять тегирование в бэкенде — правильно в перспективе (передано бэкенду), но это зона бэкенда;
LLM-нормализация каждой новости — расход бюджета на каждое событие ленты.
**Последствия.** Отложенный набор: шум 0,073 → 0,033, recall важных 0,94 → 1,0; демо-лента: nDCG@5 CEO 0,88 → 0,94.
Правки сделаны по ошибкам набора №1 — для чистой оценки нужен набор №2 (`NEXT_STEPS.md` §4).

## ADR-ML-010. Скрининг события перед подверженностью (живая лента)

**Контекст.** Разбор живой ленты dev-стенда (331 событие RSS, `reports/live_feed.md`): 74% показанного нерелевантно,
164 карточки нерелевантных событий — с уровнем «высокое/критическое». Классы: иностранные ЦБ, отчёты и кражи
(«FedEx») как ключевая ставка; омонимы и подстроки тегера («медики» → медь, «в прокат выходят» → прокат,
«Чугунный мост» → металлы); санкционные и военные заголовки без адресата; упоминание страны ВЭД без торговли;
инциденты отдельных фирм как «изменение отрасли контрагентов»; англоязычные новости о США.
**Решение.** `profile.normalize_event` + `screen_event` (детерминированно, по словам заголовка, лида и тела новости):
- нет экономического содержания → остаются только прямые связи (группа, названный контрагент);
- канал «ставка» — только ключевая ставка Банка России в русском заголовке без иностранного ЦБ; упоминание ставки
  только в тексте (обзор рынка, дайджест) → вес ×0,25;
- общая чувствительность к ВЭД (санкции, курс) — только при упоминании России и торговли/платежей;
  страна ВЭД — только вместе с торговым контекстом;
- канал «отрасль контрагентов» — только при изменении условий рынка (цены, тарифы, дефицит, спрос, пошлины);
- новость о загранице без России (англоязычная или с зарубежной географией в заголовке) → веса ×0,35;
- теги сырья/отраслей из омонимов снимаются, если нет словоформы с границами (`_TAG_CUES`);
- FX-заголовок («Рубль вырос к юаню»), который тегер отнёс к `other`, считается FX-событием.
**Результат.** Живая лента: шум 74% → 41%, нерелевантных «высоких/критических» 164 → 9, recall важных 0,96 → 1,0,
recall фоновых 0,93 → 0,83 (цена правки). Демо-лента и отложенный набор без регрессии (шум 0,20 и 0,025).
**Альтернативы.** Исправление тегера бэкенда — правильно и передано бэкенду (`NEXT_STEPS.md`); LLM-фильтр каждой новости
— расход бюджета на весь поток. Скрининг на правилах — защитный слой ML независимо от качества тегов.
**Риски.** Словари ключей: новые формулировки проходят мимо; набор `eval/live/` — регрессия, его стоит пополнять
реальными провалами со стенда.

**Дополнение к ADR-ML-010 (слепой набор №2, 24.10).** Правило «ставка не в заголовке → ×0,25» на слепом наборе
обнулило recall важных (0,06): заголовки «прогноз по средней ставке», «ЦБ мог бы снизить ставку» не содержат слов
«ключевая ставка». Заголовок теперь «про ставку» при любом слове «ставка/ДКП/ДКУ». Отчёт — `reports/heldout_set2.md`.

## ADR-ML-011. ml-ranker@2: эмбеддинги + обученная модель поверх правил

**Контекст.** Правила (ADR-ML-009/010) зависят от ключевых тегов бэкенда и словарей: на новых формулировках они
либо пропускают («прогноз по средней ставке»), либо шумят. Нужна оценка, которая читает смысл новости и держит
качество на полностью новых данных.
**Решение.** Для пар (компания, событие) с хотя бы одним каналом подверженности агент считает вероятность
релевантности обученной логистической регрессией (`alfa_ml/ranker2.py`, веса — `alfa_ml/models/ranker2.json`):
- 32 признака правил: веса каналов `compute_exposure`, оценка ml-ranker@1, число каналов, магнитуда, флаги скрининга,
  тип события;
- 5 семантических признаков (`alfa_ml/semantic.py`, `paraphrase-multilingual-MiniLM-L12-v2` через fastembed/ONNX на CPU,
  ~25 мс на текст, без LLM): близость события к описаниям «что двигает бизнес» (ставка, курс, санкции, металлы,
  стройка, агро, удобрения, топливо, логистика, спрос, налоги, макро) и «что не двигает» (инциденты, культура/спорт,
  зарубежная политика, экономика США/ЕС), их разность, совпадение концепта с потребностями компании
  (`company_needs` — только из `company_context`), близость к текстовому профилю компании.
Карточка показывается при вероятности ≥ порога (0,86), выбранного out-of-fold так, чтобы recall важных был ≥ 0,95.
Score и разбивка в `relevance` — от ml-ranker@2, в трассе — вероятность и 5 главных вкладов признаков.
**Оценка** (`eval/train_ranker2.py`, `reports/ranker2.md`): перекрёстная проверка «один набор в тест» по четырём
размеченным наборам (демо, Интерфакс-1, живая лента, слепой №2); состав признаков и регуляризация выбраны только по ней.
Среднее: nDCG@5 0,736 → 0,865, доля мусора 19% → 11%, recall важных 1,0. Слепой набор №3 (30 новостей РБК × 10 новых
реальных клиентов, разметка закоммичена до обучения): nDCG@5 0,516 → 0,551, мусор 28% → 20%, recall важных 1,0,
recall фоновых 0,76 → 0,69.
**Отвергнуто по абляции:** кросс-энкодер `jina-reranker-v2-base-multilingual` (минус на Интерфакс-1, nDCG 0,83 → 0,63,
и 0,4 с на пару на 2 vCPU — выключен, `ML_RERANKER_MODEL` для экспериментов); 28 признаков по отдельным концептам
(нестабильны между наборами); градиентный бустинг (переобучается на ~250 положительных примерах).
**Деградация.** Нет fastembed/весов модели или ошибка в признаках → ml-ranker@1 и порог 0,35 (как раньше).
Модель встраивается в образ при сборке (`ml/Dockerfile`, `FASTEMBED_CACHE_PATH=/app/models`, `HF_HUB_OFFLINE=1`).
**Риски.** Обучение на 2180 парах (247 релевантных), из них 1655 — живая лента пяти демо-компаний; кандидаты всё ещё
ограничены каналами правил (семантика отсекает шум, но не добавляет пропущенные связи). Переобучение —
`python -m eval.semantic_store dump && … compute && python -m eval.train_ranker2` после пополнения разметки.

**Дополнение к ADR-ML-011 (слепой набор №4, 25.10): kNN-память разметки.** Первая версия ml-ranker@2 на новом
источнике («Коммерсантъ», 40 новостей × 10 новых реальных клиентов, разметка закоммичена до прогона,
`reports/ranker2_blind_set4.md`) срезала шум 48% → 18%, но пропустила одну важную пару (p = 0,85 при пороге 0,86) и
половину фоновых: порог «максимум точности при recall важных ≥ 0,95» оказался хрупким. Изменения:
- **kNN-память разметки** (`models/ranker2_memory.npz`, только векторы и метки, без текстов): для пары считаются метки
  самых похожих размеченных пар — близость событий⁴ × близость компаний²; признаки `knn_rel`, `knn_imp`, `knn_mass`.
  Так человеческая разметка переносится на новые формулировки и новые компании. На обучении kNN-признаки строки
  считаются без её собственного набора (утечки нет); в сервисе — по всей памяти;
- порог — лучший F1 по релевантным при recall важных ≥ 0,95 (вместо максимума точности);
- наборы №3 и №4 после просмотра стали обучающими (6 наборов, 2880 пар, 301 релевантная).
«Один набор в тест» по 6 наборам: ml-ranker@1 — nDCG@5 0,667, мусор 25%, recall важных 1,0, фоновых 0,71;
первая версия ml-ranker@2 — 0,732 / 22% / 0,94 / 0,66; текущая — **0,773 / 21% / 1,0 / 0,64**. Реранкер и бустинг
по-прежнему хуже. Слабое место — набор №4: у половины его релевантных пар нет ни одного канала правил, а
обученная модель решает только среди кандидатов правил (nDCG 0,47 против 0,54 у правил). Следующий слепой набор
(№5, новый источник) — `eval/eval_ranker2.py`.

**Слепой набор №5 (25.10, после выкладки версии с kNN-памятью).** «Ведомости» (новый источник; лента наполовину из
политики), 40 событий × 10 новых реальных клиентов, разметка закоммичена до прогона, проверялась поставляемая
модель как есть (`reports/ranker2_blind_set5.md`): ml-ranker@1 → ml-ranker@2 — мусор 39% → 18%, recall важных
0,75 → 0,75 (обе пропускают «россияне реже путешествуют» для гостиницы: нет канала правил), recall фоновых
0,65 → 0,43, nDCG@5 0,53 → 0,45. Вывод: на полностью новых данных ml-ranker@2 вдвое чистит ленту, но отсекает
часть фоновых связей (МРОТ для трудоёмких бизнесов, рынок коммерческой недвижимости) и ранжирует не лучше правил.
Следующий шаг — кандидаты без каналов правил (семантический канал «потребность компании × тема события») и
