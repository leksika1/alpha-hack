# Качество AI-компонентов: метрики, мониторинг, деградация, сопровождение

## 1. Офлайн-оценка (перед каждым релизом промптов/моделей)

`ml/eval/run_eval.py` — 5 демо-компаний × 15 событий демо-ленты, разметка `eval/labels.json` (0/1/2).

| Метрика | Что показывает | Цель |
|---|---|---|
| nDCG@5, P@3, P@5 по компаниям | порядок ленты | ≥ baseline бэкенда |
| Recall важных (gold=2) | не пропускаем важное (главный риск кейса) | 1,0 |
| Доля нерелевантных в показанных | шум ленты | ≤ 0,25 |
| Доля инсайтов, прошедших валидатор бэкенда | контракт и правила | 100% |
| Groundedness — доля утверждений со ссылкой | связь с источниками | ≥ 95% (факты — 100%) |
| Признаков компании в «почему важно» | персонализация | ≥ 2 |
| Пересечение сути с текстом новости | пересказ vs интерпретация | ≤ 0,5 |
| Доля с позицией банка / с количественной оценкой | ценность аналитики банка | растёт |
| Вызовов LLM, токенов и ₽ на инсайт, задержка p95 | экономика | ≤ 2,5 ₽, p95 ≤ 40 с |

С LLM (после получения ключа): тот же прогон с `--llm-base-url`; дополнительно LLM-as-judge по рубрике критика
(обоснованность, атрибуция, персонализация, глубина 1–5) на 30 инсайтах + ручная проверка экспертом 10 из них.

`ml/eval/heldout/` — отложенные наборы: свежие новости × реальные клиенты, разметка по профилям **до** прогона,
порог не меняется (`run_eval --news … --labels … --data-dir ../data/raw`). Набор, по ошибкам которого делались правки,
дальше считается обучающим; для отчёта — новый.

`ml/eval/live/` — живая лента dev-стенда (реальный «грязный» RSS) как регрессия по шуму: доля нерелевантного,
нерелевантные с высоким уровнем влияния, recall важных и фоновых (`reports/live_feed.md`).

`ml/eval/train_ranker2.py` — обучение и проверка ml-ranker@2 (ADR-ML-011): «один набор в тест» по всем размеченным
наборам + финальный слепой набор (`reports/ranker2.md`). Состав признаков выбирается только по перекрёстной проверке;
слепой набор размечается и коммитится до обучения. В трассе каждого решения — вероятность и главные вклады признаков.

`ml/eval/real_analytics.py` — реальные PDF банка через OCR бэкенда → чанки → `run_eval --analytics …`: доля инсайтов с
позицией банка, дословность цитат, отсутствие притянутых материалов.

`ml/eval/real_profiles.py` — устойчивость на реальных профилях клиентов (сколько событий доходит до компании,
доля компаний без событий, валидность).

## 2. Онлайн-метрики (данные бэкенда: отзывы, клики, скрытия)

| Метрика | Источник | Тревога |
|---|---|---|
| Доля «полезно» среди оценённых инсайтов, по типу события и фактору | `feedback` | падение > 20% за неделю |
| Доля скрытий («не про нас») по фактору `relevance.breakdown` | `insight_state` | фактор с долей скрытий > 30% → пересмотр калибровки |
| CTR карточки, раскрытие «На чём основан вывод», переходы к источнику | события фронта | — |
| Вопросы в чате на инсайт, доля ответов с источниками | `/ask` | ответы без источников > 10% |
| Доля `skipped` / `failed`, доля fallback rules@1 | `infer_complete` в логах ML | fallback > 10% (`docs/ml`: признак проблем LLM) |
| Доля отклонённых валидатором бэкенда | `/admin/metrics` | > 1% |
| ₽ и токены в день, на инсайт; задержка p95 | `llm_usage`, `/admin/llm-usage` | 80% дневного бюджета |

Север: доля сессий с полезным инсайтом (CJM) — ML влияет через точность топа ленты и глубину интерпретации.

## 3. Процесс

1. Еженедельно: выборка 30 инсайтов (стратифицированно по типу события и уровню влияния) → эксперт банка
   размечает «релевантно / обосновано / позиция банка верна» → пополняет `eval/labels.json` и набор для судьи.
2. Скрытия и «не полезно» с комментариями → разбор причин → правка калибровки (`profile.py`) или промпта.
3. Любая правка промпта — новая версия файла (`prompt: analyst@N`), прогон `eval` до и после, результат в PR.
4. Смена модели — только через `ML_MODEL_*` после сравнения на `eval` (качество, ₽, задержка).

## 4. Деградация (safe mode)

| Ситуация | Что видит пользователь | Сигнал оператору | Сценарий жив? |
|---|---|---|---|
| Нет ключа LLM / `allow_llm=false` | инсайт rules@1 (те же блоки, проще текст) | `models_used: rules@1` | да |
| Бюджет исчерпан (429) | rules@1, чат — детерминированный ответ | шаг `llm_call skipped budget_exhausted` | да |
| Провайдер 5xx / тайм-аут | rules@1 после 1 повтора | `llm_call error` | да |
| Модель вернула не JSON | 1 попытка починки, затем rules@1 | `llm_call error answer is not JSON` | да |
| Нет аналитики банка по теме | инсайт без позиции банка + дисклеймер | `retry analytics_broaden` | да |
| Инструмент недоступен (контрагенты, группа) | инсайт без этого блока | `tool_call error` | да |
| Нет контекста компании / события | `failed` (бэкенд не покажет) | `error generation_failed` | нет — проблема данных |
| Инъекция в тексте новости | предложение вырезано, текст — данные | флаг `suspected_prompt_injection` | да |

## 5. Сопровождение и масштабирование

- **Новая отрасль:** теги и флаги ОКВЭД — справочник бэкенда (`backend/data/reference/okved_*.csv`); если у
  отрасли особая механика (как ипотека для девелоперов) — шаблон в `agent/rules.py::_consequences`; LLM-путь
  работает сразу.
- **Новый тип клиента / новые признаки:** признак появляется в `company_context` → доступен как `feature_ref`;
  связь с событием — одна ветка в `profile.compute_exposure`.
- **Новый источник:** новости и аналитика приходят через Tools API — изменений в ML не нужно.
- **Версии:** промпты — файлы с версией, ранжировщик — `ml-ranker@N` в `relevance.scorer`, контракт — `schema_version`.
